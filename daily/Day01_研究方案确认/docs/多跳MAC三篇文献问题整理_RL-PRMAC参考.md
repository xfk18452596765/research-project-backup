# 一、EMAC：异步多跳路径预约MAC

## 1. PION控制帧如何沿多跳路径传播？

假设路由路径为：

```text
S → A → B → C
```

传播过程如下：

1. 源节点`S`完成DIFS侦听和随机退避后，向下一跳`A`发送PION。
2. `A`收到PION后，根据PION中的最终目的地址查询本地路由表，确定下一跳`B`。
3. `A`经过SIFS后向`B`转发PION。
4. `A`转发的PION同时承担两个作用：
   - 对上游`S`而言，相当于CTS或确认帧；
   - 对下游`B`而言，相当于RTS或新的预约请求。
5. `B`收到后以相同方式继续向`C`转发。
6. PION在以下任一条件出现时停止：
   - 到达最终目的节点；
   - PION发生丢失；
   - 新预约与已有TC或NAV冲突；
   - 中间节点主动截断预约。

PION中至少需要携带：

```text
最终目的地址
Hop Count
Data Delay Factor
数据持续时间或调度相关信息
```

### 核心结论

> 一个PION转发动作，同时完成“确认上一跳”和“预约下一跳”，因此可减少逐跳独立RTS/CTS交互。

---

## 2. EMAC如何让异步节点形成协调预约？

EMAC不要求所有节点拥有完全同步的时钟，而是让每个节点根据PION携带的跳数、控制帧持续时间和数据延迟因子，在自己的本地时钟上推算未来的数据收发时刻。

因此，EMAC实现的是：

> **预约行为同步，而不是物理时钟同步。**

节点在本地时间`NOW`收到Hop Count为`h`的PION时，可反推出源节点收到第一跳确认PION的大致时刻：

\[
t_0=NOW-(h-1)(T_{PION}+SIFS)
\]

源节点开始发送数据的时刻：

\[
t_1=t_0+T_{delay}
\]

路径上第\(x\)次数据发送的开始时刻：

\[
t_x=t_1+(x-1)(T_{data}+SIFS+T_{ACK}+SIFS)
\]

节点据此建立两类预约：

- **TC（Transmission Commitment）**：本节点未来某段时间必须执行发送或接收；
- **NAV（Network Allocation Vector）**：邻居节点在相应时间内保持静默。

即使各节点的本地时钟有不同偏移，只要它们使用相同的相对时间关系，也能够形成连续的接收—发送时间窗口。

---

## 3. 数据帧何时开始沿路径转发？

源节点不需要等待PION传播到整个路径终点。

当源节点听到第一跳节点转发的PION后，说明第一跳预约已经成功。源节点随后等待一个额外的\(T_{delay}\)，再开始发送数据。

单跳路径：

\[
T_{delay}=SIFS
\]

多跳路径：

\[
T_{delay}=SIFS+d(T_{PION}+SIFS)
\]

其中\(d\)为Data Delay Factor。

设置该延迟是为了避免数据帧过早启动并追上仍在下游传播的PION，从而在某个中继节点发生控制帧和数据帧冲突。

数据随后按流水线方式转发：

```text
S --DATA--> A --DATA--> B --DATA--> C
```

每跳仍保留：

```text
DATA → SIFS → ACK → SIFS
```

但中继节点不再重新执行完整的DIFS、随机退避和RTS/CTS。

### 核心结论

> PION在前方建立预约，数据帧在后方沿已预约路径连续跟进。

---

## 4. 预约冲突如何解决？

节点收到新PION后，会计算该PION要求建立的TC区间，并检查是否与以下内容重叠：

```text
已有TC
已有NAV
其他流已经建立的预约
本节点未来的发送或接收任务
```

冲突发生时可采用以下处理方式。

### 4.1 静默丢弃PION

节点不继续转发，也不发送确认。上游节点等待超时后结束或重试本次事务。

### 4.2 发送CTS-only PION

节点只确认上一跳，但不再向下一跳继续预约。

这表示：

> 本次预约在当前节点处被截断，数据最多连续转发到该节点。

### 4.3 取消失效预约

典型条件包括：

- 预计时间内没有收到数据；
- 同一上游节点发来新的冲突预约；
- PION或数据帧丢失导致原预约失效；
- 路由发生变化；
- 预约超过有效期。

论文未完整公开所有冲突类型和CTS-only判决细节，因此Python仿真需要自行定义清晰的冲突优先级和处理规则。

---

## 5. EMAC与DCF相比减少了哪一类竞争？

EMAC最主要减少的是：

## 同一业务流内部竞争（intra-flow contention）

在DCF中，同一个分组经过每一跳时，中继节点都需要重新竞争信道：

```text
S → A：S竞争一次
A → B：A重新竞争一次
B → C：B再次竞争一次
```

于是，上游节点和下游节点虽然服务于同一个数据流，却相互争夺信道。

EMAC通过一次PION预约未来多跳，使路径上的节点按照预约顺序依次发送，从而减少：

- 上游与下游节点之间的同流竞争；
- 每跳重复DIFS和随机退避；
- 每跳独立RTS/CTS的开销；
- 同一流在中继节点之间反复阻塞。

EMAC并没有完全消除：

- 不同业务流之间的竞争；
- 隐藏终端；
- 控制帧碰撞；
- 链路误码；
- 重传。

## 6. 哪些机制可以直接简化到Python事件仿真？

### 6.1 固定路径

第一版可以直接使用：

```python
path = [0, 1, 2, 3, 4]
```

不必一开始实现完整动态路由。

### 6.2 PION逐跳传播

PION事件可包含：

```text
flow_id
packet_id
path
current_hop
reservation_length
data_duration
data_delay_factor
```

### 6.3 PION的RTS/CTS复用

中继节点转发PION时同时完成：

```text
确认上一跳
预约下一跳
```

因此不必为每一跳单独生成CTS事件。

### 6.4 有限跳数预约

建议第一版只实现：

```text
1跳预约
2跳预约
3跳预约
```

这正好对应RL-PRMAC的动作空间。

### 6.5 TC预约表

每个节点维护：

```python
tc_list = [
    (start_time, end_time, flow_id, operation)
]
```

其中`operation`为`TX`或`RX`。

### 6.6 简化NAV

可以利用干扰邻接矩阵规定：

> 某节点预约收发期间，其一跳或两跳干扰邻居不能发起新的传输。

### 6.7 超时与预约取消

```text
PION_CONFIRM_TIMEOUT
DATA_ARRIVAL_TIMEOUT
MAX_RETRY
RESERVATION_EXPIRE_TIME
```

### 6.8 第一版使用全局仿真时钟

Python离散事件仿真本身有统一的仿真时钟。第一版可以直接使用全局时间，后续再加入：

```python
local_time = simulation_time + node.clock_offset
```

用于测试异步时钟偏移。

## 7. 哪些机制不适合直接照搬到海面船舶场景？

### 7.1 固定Data Delay Factor \(d=2\)

海面反射、船距、天线高度、传播距离和干扰范围不断变化，不能直接认为“三跳外一定不干扰”。

更合理的方案：

- 第一版使用保守固定保护跳数；
- 第二版根据信道忙碌率和碰撞率调整；
- RL版本由智能体选择预约跳数或保护间隔。

### 7.2 PION沿整条路径无限传播

船舶具有移动性，路径越长，预约期间链路变化的概率越高。

更适合：

\[
K\in\{1,2,3\}
\]

即有限长度路径预约。

### 7.3 假设路由在事务中始终有效

建议加入：

```text
route_id
route_version
reservation_expire_time
```

路由版本变化后取消旧预约。

### 7.4 直接使用802.11微秒级参数

论文中的SIFS、DIFS、CW和速率属于特定ns-2配置，不能直接作为海面VHF或其他船载无线系统的参数。

### 7.5 假设链路完全对称

海面通信可能出现非对称链路和控制帧漏听，应加入：

```text
PION丢失概率
数据帧误码率
隐藏终端
非对称链路
预约信息过期
```

### 7.6 过度依赖精确到达时刻

建议为TC增加保护时间：

\[
TC=
[t_{expected}-G_{pre},
t_{expected}+T_{frame}+G_{post}]
\]

# 二、分布式优先级调度与多跳协调

## 1. priority tag表示什么？

priority tag即优先级标签，本质上是一个可比较的数值型优先级索引。

通常：

\[
priority\ tag越小，分组优先级越高
\]

它不是固定的“高、中、低”，而是可根据调度策略动态计算。

### 1.1 EDF优先级

\[
P_i=a_i+D_i
\]

其中：

- \(a_i\)：分组到达时间；
- \(D_i\)：允许的时延上限；
- \(P_i\)：绝对截止时间。

截止时间越早，优先级越高。

### 1.2 Virtual Clock优先级

可根据以下信息递推：

```text
分组长度
目标服务速率
该流上一分组的虚拟完成时间
```

### 核心结论

> priority tag描述的是当前队首分组的紧迫程度，而不是节点永久不变的优先级。

---

## 2. 节点如何通过侦听维护本地调度表？

论文利用无线信道的广播特性，将优先级信息搭载在802.11已有帧中。

| 帧类型 | 携带的优先级信息 | 作用 |
|---|---|---|
| RTS | 当前竞争分组的priority tag | 邻居获知当前发送请求 |
| CTS | 当前分组优先级及节点信息 | 让听不到RTS的隐藏节点获得信息 |
| DATA | 发送节点下一个HOL分组的priority tag | 提前公布下一轮竞争信息 |
| ACK | DATA中HOL信息的副本 | 让听不到DATA的隐藏节点更新调度表 |

本地调度表可简化为：

```text
source_id
destination_id
priority_tag
timestamp
status
```

更新流程：

1. 侦听到RTS或CTS后，加入当前分组表项；
2. 侦听到DATA或ACK后，加入发送节点下一个HOL分组表项；
3. 成功侦听ACK后，删除已经完成的旧表项；
4. 保留下一个HOL分组，用于后续竞争排序；
5. 定时清理过期信息。

调度表可能因移动、碰撞、误码和隐藏终端而不完整。论文目标不是获得完美全局信息，而是利用部分信息逼近理想调度。

---

## 3. 优先级如何影响退避？

节点将自己的HOL分组与本地调度表中的其他分组比较，得到本节点的局部排名。

### 排名第一的节点

若本节点认为自己的分组优先级最高：

- DIFS结束后进入第一竞争阶段；
- 使用较小的CW；
- 额外等待时间较短；
- 更可能率先发送。

### 非排名第一的节点

若调度表中存在更高优先级分组：

- DIFS后额外等待；
- 第一阶段暂时不参与竞争；
- 在后续竞争窗口中接入；
- 或使用更大的CW。

总体关系：

\[
P_i越小
\Rightarrow 排名越靠前
\Rightarrow 额外等待越短
\Rightarrow CW越小
\Rightarrow 越容易先接入
\]

该机制包含：

- **contention reduction**：低优先级节点暂时退出首轮竞争；
- **collision resolution**：多个高优先级节点之间仍采用随机退避。

---

## 4. 什么是multi-hop coordination？

multi-hop coordination在该论文中指：

## 多跳优先级协调

它不同于EMAC中的多跳路径预约。

其含义是：

> 分组每经过一个中继节点，下游节点根据它在上游已经经历的服务与时延，重新调整该分组的优先级。

例如：

```text
S → A → B → C
```

若分组在`S→A`阶段因排队、碰撞或重传而严重延迟，那么它到达`A`后应提高优先级，使其在`A→B`阶段更快获得信道。

若分组在上游传输顺利、提前到达，则下游可以适当降低其相对优先级，让更紧迫的分组先通过。

---

## 5. 为什么下游节点需要补偿上游累计时延？

端到端时延是各跳时延之和：

\[
D_{e2e}
=
\sum_{h=1}^{H}
(
D_{queue,h}
+
D_{backoff,h}
+
D_{tx,h}
+
D_{retry,h}
)
\]

如果上游已经消耗过多时延预算，下游仍按普通优先级处理，该分组很可能超过端到端截止时间。

例如：

```text
端到端时限：100 ms
路径：4跳
理想每跳预算：25 ms
```

若第一跳已经耗费50 ms，剩余3跳仅剩50 ms。下游提高优先级后，可以通过缩短后续排队和退避时间，尽量补偿上游延迟。

需要注意：

> 补偿不能恢复已经消耗的时间，只能压缩剩余路径的等待时间，因此不保证一定满足截止期。

---

## 6. 哪一部分可以用于解释告警包优先接入？

### 6.1 priority tag与优先级退避

用于解释：

> 告警包为什么能更早获得信道？

可以规定：

\[
P_{alarm}<P_{normal}
\]

或：

\[
CW_{alarm}<CW_{normal}
\]

例如：

```text
告警包：CW ∈ [0, 7]
普通包：CW ∈ [0, 31]
```

### 6.2 multi-hop coordination

用于解释：

> 告警包经过多跳后为什么仍保持较高紧迫性？

可以定义：

\[
T_{remain}
=
T_{deadline}
-
(t_{now}-t_{generation})
\]

剩余时限越少，优先级越高。

### 可直接用于论文中的表述

> 告警业务在源节点通过较小竞争窗口优先接入信道；在多跳转发过程中，中继节点根据累计时延和剩余端到端时限动态提高其转发优先级，从而降低告警包在后续节点的排队与竞争等待。

---

## 7. 第一版协议是否需要完整实现该算法？

不需要，也不建议。

完整算法需要实现：

```text
RTS、CTS、DATA、ACK中的不同优先级字段
邻居帧持续侦听
本地调度表的新增、删除与过期
局部优先级排名
多阶段退避
EDF、Virtual Clock、TTL、UDB
多跳priority tag递推
不完整调度表和隐藏节点异常处理
```

这会显著增加第一版仿真的复杂度，并掩盖本研究的核心问题：多跳路径预约是否能够降低端到端时延累计。

### 第一版建议

#### 双队列

```text
alarm_queue
normal_queue
```

#### 静态差异化CW

```python
if packet.is_alarm:
    cw = CW_ALARM
else:
    cw = CW_NORMAL
```

#### 分组携带时间信息

```text
generation_time
deadline
traffic_class
```

#### 简化的累计时延补偿

```python
elapsed_delay = now - packet.generation_time
remaining_time = packet.deadline - elapsed_delay
```

当剩余时间低于阈值时，提高该分组优先级。

### 推荐迭代顺序

```text
第一版：
固定业务优先级
+ 双队列
+ 告警包小CW
+ 多跳预约连续转发

第二版：
根据累计时延动态提高优先级

第三版：
邻居priority tag广播
+ 本地调度表
+ 相对排名退避
```

# 三、EASO-TDMA：海面船舶自组织时隙分配

## 1. SANET中的中继瓶颈如何形成？

SANET以岸基基站为汇聚中心。远端船舶需要借助其他船舶逐跳转发：

```text
远端船C → 船B → 船A → 岸基基站
```

船A不仅要发送自己的数据，还要转发船B、船C的数据；下行方向上，也需要把岸基数据继续转发给远端船舶。

原始ASO-TDMA给所有船舶分配固定且相同数量的时隙，没有考虑中继负载差异，因此会出现：

\[
自身业务量+中继业务量
>
固定时隙承载能力
\]

继而导致：

```text
多条路径汇聚
→ 中继队列积压
→ 排队时延增加
→ 队列溢出
→ 丢包率和端到端时延升高
```

### 核心结论

> SANET中继瓶颈的本质，是路由汇聚负载与固定时隙资源不匹配。

---

## 2. subscribing ships数量代表什么？

某艘船\(i\)的subscribing ships指：

> 路由到岸基基站时，通信路径经过船\(i\)的全部下游船舶。

它不仅包括一跳子节点，也包括间接依赖该中继船的更远端节点。

例如：

```text
岸基
 ↑
船A
↑  ↑
B  C
↑
D
```

对于船A：

```text
subscribing ships = {B, C, D}
数量 = 3
```

递归计算：

\[
n_R(i,HN)
=
\sum_{k\in Set_R(i,HN)}
[n_R(k,HN)+1]
\]

因此，subscribing ships数量可以理解为：

- 经由本节点转发的下游节点数量；
- 节点在路由树中的汇聚程度；
- 潜在中继业务负载；
- 所需时隙容量的重要依据。

---

## 3. EASO-TDMA如何根据路由表分配时隙？

一个超帧长度为1分钟，包含5个superframe。节点在当前超帧结束时查询路由表，统计subscribing ships数量，并为下一超帧重新配置时隙。

目标时隙数：

\[
N_{SF}(i,HN+1,SN)=4n_R(i,HN)+2
\]

其中：

- 基础2个时隙用于节点自身通信；
- 每增加1艘subscribing ship，增加4个时隙；
- 增加的时隙用于支持下游船舶的上下行中继。

| subscribing ships数量 | 每个superframe目标时隙 |
|---:|---:|
| 0 | 2 |
| 1 | 6 |
| 2 | 10 |
| 3 | 14 |

节点比较当前时隙数和目标值：

- 当前值小于目标值：under-allocated，需要增加；
- 当前值大于目标值：over-allocated，需要释放；
- 两者相等：保持不变。

具体时隙位置由channel status table决定：

1. 排除岸基预留资源；
2. 优先选择空闲时隙最多的multiframe；
3. 再选择空闲程度最高的TDMA frame；
4. 最后从空闲时隙中随机选择；
5. 释放时则优先从资源较紧张的位置释放。

### 核心结论

> 路由表决定“需要多少时隙”，信道状态表决定“具体选择哪些时隙”。

## 4. 为什么固定时隙会造成利用不足或瓶颈？

### 4.1 轻载节点利用不足

若节点固定拥有10个时隙，但实际只使用2个：

\[
CU=rac{2}{10}=20\%
\]

其余固定时隙被浪费。

### 4.2 重载中继节点形成瓶颈

```text
普通节点：自身5个包，拥有10个时隙
中继节点：自身5个包+转发30个包，仍只有10个时隙
```

中继节点因此出现严重排队积压。

### 根本原因

\[
资源分配不随业务负载和路由负载变化
\]

固定分配会同时造成：

- 轻载节点资源浪费；
- 重载节点资源不足；
- 容量分布与业务汇聚位置不一致；
- 多跳排队时延累计。

## 7. EASO-TDMA与本研究的竞争型路径预约有什么本质区别？

| 对比维度 | EASO-TDMA | Fixed-PRMAC / RL-PRMAC |
|---|---|---|
| 接入方式 | 无竞争TDMA | CSMA/CA竞争接入 |
| 时间同步 | 依赖GPS和统一时隙结构 | 可支持异步节点 |
| 资源单位 | 预先占有的周期性时隙 | 临时获得的多跳传输机会 |
| 调整依据 | subscribing ships数量 | 队列、忙碌率、重传、剩余跳数等 |
| 调整周期 | 超帧级，约1分钟 | 分组级或预约事务级 |
| 多跳方式 | 每跳在自己的时隙中存储转发 | 一次竞争后连续预约1—3跳 |
| 主要目标 | 解决中继容量分配不均 | 减少每跳重复竞争和时延累计 |
| 冲突处理 | 避免选择已占用时隙 | PION竞争、退避、TC冲突检查 |
| 强化学习 | 不使用 | 可动态选择预约长度和CW |

最本质的区别：

\[
EASO	ext{-}TDMA：
按中继负载分配周期性时隙容量
\]

\[
RL	ext{-}PRMAC：
按当前状态获取临时多跳连续转发权
\]

EASO-TDMA解决的是：

> 某个中继节点未来一段时间应该拥有多少资源？

RL-PRMAC解决的是：

> 当前数据包竞争成功后，应该连续预约多少跳，以及使用多大的竞争窗口？

## 4. 建议的RL-PRMAC状态空间

基础状态：

\[
s=(Q_i,B_i,R_i,H_i)
\]

其中：

- \(Q_i\)：当前节点队列长度；
- \(B_i\)：信道忙碌率；
- \(R_i\)：近期重传次数；
- \(H_i\)：剩余跳数。

结合三篇文献后，可扩展为：

\[
s=(Q_i,B_i,R_i,H_i,P_i,L_i)
\]

其中：

- \(P_i\)：当前分组优先级或剩余时限等级；
- \(L_i\)：中继负载，可由转发队列长度、经过本节点的流数量或subscribing ships近似表示。

## 5. 建议的动作空间

\[
a=(K,CW)
\]

其中：

\[
K\in\{1,2,3\}
\]

\[
CW\in\{CW_{small},CW_{large}\}
\]

可形成6个离散动作：

```text
1跳预约 + 小CW
1跳预约 + 大CW
2跳预约 + 小CW
2跳预约 + 大CW
3跳预约 + 小CW
3跳预约 + 大CW
```

后续可扩展：

```text
保护间隔
是否截断预约
告警包抢占等级
保守或激进重传策略
```

# 五、快速查询表

| 问题 | 一句话答案 |
|---|---|
| PION如何传播？ | 沿既定路由逐跳转发，每次转发同时确认上一跳并预约下一跳。 |
| EMAC如何协调异步节点？ | 节点根据PION中的跳数和帧时长，用本地时钟推算未来收发时刻。 |
| 数据何时启动？ | 源节点收到第一跳转发PION后，等待保护间隔再发送。 |
| EMAC减少什么竞争？ | 主要减少同一业务流上下游节点之间的重复竞争。 |
| priority tag是什么？ | 表示队首分组紧迫程度的可比较数值，通常越小越优先。 |
| 优先级如何影响退避？ | 高优先级包更早进入竞争并使用更小CW。 |
| multi-hop coordination是什么？ | 下游节点根据上游累计时延动态调整分组优先级。 |
| 告警包如何优先接入？ | 小CW、较短额外等待、较高队列优先级和剩余时限补偿。 |
| subscribing ships是什么？ | 路由到岸基时经过某中继船的全部下游船舶。 |
| SANET瓶颈怎么形成？ | 路由汇聚导致中继业务量超过固定时隙容量。 |
| EASO-TDMA如何分配时隙？ | 路由表决定时隙数量，信道状态表决定具体时隙位置。 |
| EASO-TDMA与RL-PRMAC区别？ | 前者周期性分配容量，后者分组级竞争并预约连续多跳。 |
