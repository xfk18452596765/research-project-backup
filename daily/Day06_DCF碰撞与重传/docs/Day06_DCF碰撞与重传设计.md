# Day06：DCF碰撞、ACK超时与重传设计

## 一、设计目的

Day04只验证信道始终空闲时的DCF成功链路，Day05增加载波侦听、DIFS重启和退避冻结。Day06进一步引入两个独立发送节点，使仿真器能够表达多个节点在同一个退避时隙同时发送造成的碰撞，以及碰撞后的ACK超时、二进制指数退避和重传。

这一能力是后续构建传统多跳DCF基线的必要前提，因为多跳时延累计不仅来自逐跳排队和退避，也来自共享中继附近的碰撞与重传。

## 二、分布式执行与共享信道判定

每个节点仍然独立维护：

- 本地发送队列；
- MAC状态；
- 当前CW；
- 当前剩余退避槽数；
- 当前数据包重传次数；
- 本地随机退避选择。

`DCFContentionCoordinator`只负责仿真共享介质在同一时隙收到的发送意图，并判断一个还是多个节点同时开始发送。它代表信道层的碰撞判定，不替节点选择动作，也不构成集中式MAC调度。

## 三、为什么需要同一时隙统一判定

若第一个节点退避归零后立即将信道标记为忙，第二个同一时隙归零的节点会错误地看到信道已忙并冻结，从而无法产生真实DCF碰撞。

因此Day06采用两步处理：

```text
BACKOFF_EXPIRE
→ 注册本时隙发送意图
→ TX_SLOT_RESOLVE统一处理同一时刻的全部意图
```

若发送意图数量为1，则发送成功；若数量大于1，则这些节点同时发送并发生一次共享信道碰撞。

## 四、碰撞后的状态推进

```text
TX_START
→ COLLISION
→ TX_END
→ 等待ACK
→ ACK_TIMEOUT
```

ACK超时后：

```text
retries = retries + 1
CW_new = min(2×CW_old+1, CWmax)
```

默认参数下：

```text
CWmin=15
第一次碰撞后CW=31
第二次碰撞后CW=63
……
最大不超过1023
```

若重传次数超过`retry_limit`，数据包出队并进入`DROPPED`状态；否则重新执行完整DIFS并在新CW范围内选择退避值。

## 五、Day06确定性演示场景

两个节点都在0秒产生一个1024字节数据包，目标节点均为节点2。

第一次竞争：

```text
节点0退避=0
节点1退避=0
→ 同一时隙发送
→ 碰撞
```

第一次重传：

```text
节点0退避=0
节点1退避=1
```

因此节点0先发送成功；节点1冻结剩余1个时隙，待节点0完成ACK后重新等待DIFS，再完成剩余退避并成功发送。

## 六、预期关键结果

```text
collision_count=1
packet0_retries=1
packet1_retries=1
最大观察CW=31
packet0_delay=0.008812秒
packet1_delay=0.013238秒
两个数据包均DELIVERED
信道最终空闲
```

## 七、与后续任务的关系

Day06只解决单碰撞域内的碰撞和重传。后续才能在此基础上加入：

- 多数据包随机到达；
- 多节点持续竞争；
- 多跳逐跳转发；
- 中继队列拥塞；
- DCF端到端时延累计实验；
- Fixed-PRMAC路径预约；
- RL-PRMAC自适应预约。
