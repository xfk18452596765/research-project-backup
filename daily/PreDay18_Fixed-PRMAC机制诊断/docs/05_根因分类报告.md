# Fixed-PRMAC 根因分类报告

## 结论

```text
MIXED_ROOT_CAUSE
```

原 FAIL 同时受到明确的 ns-3 shim 实现伪影与仍未消除的协议机制风险影响。
该分类不改变 PreDay18 的 `FAIL`，Day18 继续锁定。

## 十个必答问题

1. **原拓扑是否真实多跳？** 否。原文件 61—66 行没有设置节点坐标，并使用
   `FixedRssLossModel(-80 dBm)`；任意节点对具有相同传播损耗，等效全连接。
2. **DCF 是否因果转发？** 否。原文件 72—82 行预先调度所有 hop；中继接收失败
   不会阻止后续 hop。
3. **Fixed 是否真实 K=2？** 否。每 hop 重复完整 PR_REQ/PR_ACK/DATA/H_ACK/RELEASE，
   没有一次预约覆盖最多两跳的段。
4. **预约是否改变底层接入？** 否。DATA 仍作为普通 UDP 包进入
   `AdhocWifiMac/DCF`，没有 MAC 保护窗。
5. **未交付包丢在哪里？** 诊断 trace 将其定位为 socket 接收拒绝、MAC 丢弃、
   PHY 接收丢失或仿真停止时未到达终点。高负载原 Fixed 聚合为
   86 `PHY_RX_DROP`、404 `SIMULATION_STOP_TIMEOUT`、110 `DELIVERED`；
   `UNKNOWN_LOSS=0`。
6. **实现错误对原 FAIL 的贡献？** 很大且已确认。仅把全连接改为位置链，
   Fixed 从 18.33% 提升到 65.17%；真实 K=2 分段从 18.33% 提升到 39.17%。
   原预调度还破坏了端到端因果语义。
7. **是否仍有协议风险？** 是。组合参考中 Fixed 23.67%，仍低于 DCF 35.67%；
   仅应用层 reservation-window 没有改善，说明控制开销仍通过 DCF 竞争，
   且缺少真正 MAC 保护。
8. **最终根因分类？** `MIXED_ROOT_CAUSE`。实现错误与协议风险同时存在。
9. **原 FAIL 应如何解释？** 它是对当时 ns-3 shim 的真实失败观测，不能作为
   完整 K=2 Fixed-PRMAC 原生 MAC 的纯协议定论；但也不能因实现错误而改判。
10. **Day18 是否锁定？** 是。只有后续独立止损任务通过后才可解锁。

## 额外实现审计

- `Create<Packet>(bytes)` 后再加 `SeqTsHeader`，线上大小超过配置值；
- BEB 使用 `15*2^n` 且 20 us/10 us 时隙混用，不满足冻结公式；
- hidden terminal 只是 5% Bernoulli 控制丢失；
- `flows` 参数解析后没有生成多条流；
- 原 `dropped=created-delivered` 无法区分栈边界。

这些事实与精确行号保存在 `results/audit/static_audit.json`。
