## 1. EMAC解决了什么问题，核心机制是什么？

IEEE 802.11 DCF主要面向单跳网络。在多跳转发中，同一个数据包每经过一跳，中继节点都需要重新执行：

\[
DIFS+	ext{随机退避}+RTS/CTS+DATA/ACK
\]

因此会出现两类问题：

1. **逐跳重复竞争开销**：每一跳都重新退避、握手和重传；
2. **同流竞争**：同一路径上的上下游节点虽然转发同一条业务流，却相互争夺信道。

这些开销会随跳数逐步累加，导致端到端时延增大、吞吐量下降。

EMAC使用PION控制帧沿既定路由逐跳传播，为后续数据传输建立多跳预约。路径上的节点提前计算未来的接收和发送时间，并通过TC与NAV避免冲突。预约建立后，数据可以沿已预约路径连续转发，中继节点不必在每一跳重新执行完整的DIFS、随机退避和RTS/CTS。

**一句话总结：**

> EMAC通过PION把逐跳独立竞争变成一次源端竞争后的多跳协调转发，从而减少同流竞争和重复接入开销。

## 2. PION与RTS/CTS是什么关系？

传统DCF在每一跳采用：

```text
RTS → CTS → DATA → ACK
```

EMAC中的PION具有复用功能。假设路径为：

```text
S → A → B → C
```

传播过程为：

```text
S --PION--> A --PION--> B --PION--> C
```

其中：

- `S→A`的PION，对A而言相当于RTS；
- A向B转发PION时：
  - 对上游S而言，相当于CTS或确认；
  - 对下游B而言，相当于新的RTS；
- B向C转发时，同样同时完成确认上一跳和预约下一跳。

**一句话总结：**

> 中继节点转发的PION同时承担“上一跳CTS”和“下一跳RTS”的作用，把多个单跳握手连接成一条多跳预约链。

## 3. Kanodia的priority tag如何影响竞争？

priority tag是数据包的优先级索引，用于表示当前队首分组的紧迫程度。一般规定：

\[
priority\ tag越小，优先级越高
\]

例如在EDF调度中：

\[
P_i=a_i+D_i
\]

其中：

- \(a_i\)：数据包到达时间；
- \(D_i\)：允许的时延上限；
- \(P_i\)：绝对截止时间。

节点通过侦听RTS、CTS、DATA和ACK获得邻居队首分组的priority tag，并维护本地调度表。随后，节点将自己的队首分组与其他分组比较，得到局部优先级排名。

高优先级节点通常：

- 更早进入竞争；
- 使用更小的竞争窗口；
- 额外等待时间更短；
- 更容易先获得信道。

总体关系为：

\[
priority\ tag越小
\Rightarrow 排名越靠前
\Rightarrow CW越小
\Rightarrow 平均退避越短
\Rightarrow 越容易优先接入
\]

第一版RL-PRMAC不需要完整实现邻居priority tag调度表，只需保留：

```text
告警包：较高优先级或较小CW
普通包：普通优先级或较大CW
```

**一句话总结：**

> priority tag通过改变节点的相对排名、竞争窗口和进入竞争的时间，使紧急数据包获得更高的优先接入概率。

## 4. multi-hop coordination为什么能够补偿上游累计时延？

端到端时延由各跳时延累加而成：

\[
D_{\mathrm{e2e}}
=
\sum_{h=1}^{H}
\left(
D_{\mathrm{queue},h}
+
D_{\mathrm{backoff},h}
+
D_{\mathrm{tx},h}
+
D_{\mathrm{retry},h}
ight)
\]

如果一个数据包在上游因为排队、碰撞或重传消耗了过多时间，它到达下游节点后，剩余端到端时延预算就会减少。

multi-hop coordination的做法是：

1. 数据包携带上游优先级或时间信息；
2. 下游节点计算数据包已经经历的累计时延；
3. 若数据包在上游延迟过大，则提高其下游优先级；
4. 通过更短退避或更优先的排队，减少后续等待时间。

例如：

```text
端到端时限：100 ms
第一跳已消耗：50 ms
剩余3跳只剩：50 ms
```

如果下游仍按普通业务处理，数据包可能超时；提高其后续优先级，可以压缩剩余路径的排队和竞争时延。

需要注意：

> 多跳协调不能消除已经发生的延迟，只能通过减少后续时延，使数据包尽可能追赶端到端目标。

**一句话总结：**

> 下游节点根据上游已消耗的时延动态提高数据包优先级，用后续更快的转发补偿前面过长的等待。

## 5. SANET中的中继瓶颈如何形成？

SANET通常以岸基基站为汇聚中心。远端船舶无法直接连接岸基，需要通过其他船舶逐跳转发：

```text
远端船C → 船B → 船A → 岸基基站
```

靠近岸基或处于多条路由汇聚位置的船A需要处理：

```text
自身产生的数据
+ 船B的中继数据
+ 船C的中继数据
+ 其他下游船舶的数据
```

原始固定时隙机制给不同船舶分配相同数量的资源，没有考虑各节点中继负载不同。因此可能出现：

\[
自身业务量+中继业务量
>
节点固定资源的承载能力
\]

随后形成：

```text
多条路由汇聚
→ 中继节点入队数据增多
→ 发送资源不足
→ 队列持续积压
→ 排队时延增加
→ 队列溢出和丢包
→ 端到端性能下降
```

**一句话总结：**

> SANET中继瓶颈是由多条船岸路由在某些中继节点汇聚，而这些节点获得的发送资源没有随中继负载增加而形成的。

## 6. subscribing ships数量代表什么？

某艘船\(i\)的subscribing ships，是指：

> 路由到岸基基站时，数据路径需要经过船\(i\)的全部下游船舶。

它不仅包括直接将船\(i\)作为下一跳的船舶，也包括这些船舶后面的间接下游节点。

例如：

```text
岸基
 ↑
船A
↑  ↑
B  C
↑
D
```

对于船A：

```text
subscribing ships = {B, C, D}
数量 = 3
```

虽然D不直接连接A，但D的数据路径经过B和A，所以D仍属于A的subscribing ship。

递归关系可表示为：

\[
n_R(i)
=
\sum_{k\in Set_R(i)}
\left[n_R(k)+1ight]
\]

subscribing ships数量能够近似反映：

- 经过该节点的路由数量；
- 节点在路由树中的汇聚程度；
- 节点潜在的中继业务量；
- 节点成为瓶颈的风险。

在RL-PRMAC中，可以将其思想转换为以下状态：

```text
中继队列长度
经过本节点的活跃流数量
下游依赖节点数量
单位时间内收到的中继数据量
```

**一句话总结：**

> subscribing ships数量表示有多少下游船舶依赖当前节点把数据转发到岸基，是衡量中继汇聚负载的重要指标。

## 7. 三篇文献分别支撑RL-PRMAC的哪一部分？

| 文献 | 核心贡献 | 对RL-PRMAC的支撑 |
|---|---|---|
| **EMAC** | PION多跳预约、TC/NAV、异步协调、连续转发 | 提供Fixed-PRMAC和RL-PRMAC的协议骨架 |
| **Kanodia多跳调度** | priority tag、差异化退避、多跳时延补偿 | 支撑告警包优先接入和业务优先级状态 |
| **EASO-TDMA** | SANET中继瓶颈、subscribing ships、自适应资源分配 | 支撑海面应用场景、中继负载状态和实验指标 |

### EMAC支撑的部分

```text
PION逐跳传播
确认上一跳并预约下一跳
有限路径预约
节点TC时间区间
预约冲突检查
预约截断
DATA-ACK连续转发
减少同流竞争
```

在本研究中：

- Fixed-PRMAC固定预约跳数和CW；
- RL-PRMAC根据状态动态选择预约跳数\(K\)和CW；
- 两者的执行层都建立在EMAC式路径预约骨架上。

### Kanodia文献支撑的部分

```text
告警业务与普通业务区分
业务优先级进入状态空间
高优先级业务使用更小CW
累计时延与剩余截止时间
下游节点对上游延迟进行补偿
```

可简化为：

\[
P_i\in\{\mathrm{alarm},\mathrm{normal}\}
\]

或：

\[
T_{\mathrm{remain}}
=
D_{\mathrm{deadline}}
-
D_{\mathrm{elapsed}}
\]

### EASO-TDMA支撑的部分

```text
岸基汇聚型SANET场景
靠近岸基的中继瓶颈
路由负载应参与资源决策
subscribing ships作为中继负载指标
端到端时延、接收成功率、碰撞率、信道利用率
```

在RL-PRMAC中，不直接照搬其TDMA结构，而是将中继负载转化为状态变量，例如：

\[
L_i=Q_{\mathrm{relay},i}
\]

### 总结

> EMAC解决“如何进行多跳路径预约”，Kanodia解决“谁应优先竞争及如何补偿累计时延”，EASO-TDMA解决“为什么海面汇聚网络需要感知中继负载”。
