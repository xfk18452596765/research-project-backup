# Day13：完整Fixed-PRMAC与止损检查设计

## 1. 设计边界

Day13只完成Fixed-PRMAC验证，不包含强化学习。协议仍是分布式竞争型CSMA/CA路径预约MAC，固定`K=2`、固定`CW_init=15`。

## 2. 完整端到端控制器

`FixedPRMACEndToEndController`继承Day12控制器，不修改Day03—Day12稳定文件。每个数据包建立一个端到端会话，每个预约段保存独立状态：

- 初始接入CW与退避槽；
- 重试序列ID；
- 成功预约ID；
- DATA/H_ACK转发ID；
- 有效K；
- 重试次数；
- 释放时间；
- 失败原因。

长路径按固定K切分。例如6跳：

```text
0→1→2 | 2→3→4 | 4→5→6
```

前一段完成DATA/H_ACK并传播完RELEASE后，才允许下一段开始初始接入，避免自身前一段活动预约与下一段发生资源冲突。

## 3. 初始接入补全

Day12只在PR_NACK后模拟DIFS与BEB。Day13补充每个新预约段的首次接入：

```text
B0 ~ UniformInteger[0, 15]
T_access = DIFS + B0 × slot_time
```

重试仍使用Day12的BEB。这样Fixed-PRMAC不再获得“首次预约零竞争等待”的不公平优势。

## 4. 端到端交付统计边界

Day11在最终DATA到达时写入`delivered_at`，而DCF在ACK成功时写入。Day13不修改Day11，而是在最终H_ACK接收时覆盖Fixed-PRMAC的`delivered_at`，使两种协议都以确认完成作为交付边界。

RELEASE继续执行并计入控制开销，但不延长数据包交付时延。吞吐量测量截止到最后一个已交付数据包的确认完成时刻。

## 5. 公平比较指标

- 平均、P95、P99端到端时延；
- 投递率；
- 吞吐量；
- DCF碰撞 / Fixed-PRMAC资源冲突；
- 重传或预约重试；
- 控制帧与控制字节；
- DATA与ACK/H_ACK；
- 每包总帧数和总字节数；
- Fixed-PRMAC运行结束后是否残留ACTIVE预约。

DCF总帧/字节采用同一口径重构：每次成功或碰撞的数据发送视为一个DATA尝试，每个成功跳对应一个ACK。

## 6. 止损判定

不设置“必须提升20%”等武断百分比。Day13-Fix02将必要判据严格对齐原研究假设：较长路径和较强竞争下，路径预约应减少逐跳重复竞争。判定综合：

1. 参数公平性与Fixed-PRMAC功能完整性；
2. DCF时延随跳数增长趋势；
3. `4跳-high`、`6跳-medium`、`6跳-high`三个核心目标单元全部获胜；
4. 4/6跳、中/高负载四个关键单元至少赢3个；
5. 关键单元至少3个具有多数种子方向一致性；
6. 关键单元和全部9个单元均无投递率下降；
7. Fixed-PRMAC无本地FIFO溢出。

9个单元是否取得多数胜利继续完整报告，但作为描述性适用边界，不作为PASS门槛。2跳与低负载中的控制开销代价不得删除或隐藏。

输出：

- `PASS`：证据一致，可在完成本地回归与人工复核后进入Day14；
- `HOLD`：证据混合，停留Day13进行最小修正；
- `FAIL`：功能、公平性或主要趋势失败，必须修复并重跑。
